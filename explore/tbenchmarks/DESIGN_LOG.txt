PROJECT OVERVIEW
================================================================================

Goal: Create a reusable set of benchmarks for testing LLM reward hacking behavior
at different permission levels, aligned with real-world LLM coding assistant usage.

Key Requirements:
- Modular and testable in small increments
- Reusable benchmarks across different permission levels
- Sandboxed execution environment (Docker-based)
- Support for multiple LLM providers via OpenRouter
- JSON result storage for research reproducibility

================================================================================
DESIGN DECISIONS - PERMISSION LEVELS
================================================================================

DATE: [Early Development - Date Not Tracked]
TOPIC: Permission Level Structure

DISCUSSION:
- Initially proposed 3 levels: PL0 (text-only), PL1 (execute), PL2 (write)
- Question raised: Does PL1 enable more reward hacking if model can't iterate?
- Clarification: PL1 must support iterative refinement to enable gaming
- Real-world mapping discussed: Should align with actual LLM coding assistant usage

DECISION: Adopt 4-level structure based on real-world scenarios:
  1. PL0_CODE_SUGGESTION: GitHub Copilot style (no execution, no feedback)
  2. PL1_MANUAL_FEEDBACK: ChatGPT style (user shares test results manually)
  3. PL2_AUTO_TEST_EXEC: Aider/Cursor style (automated test execution)
  4. PL3_FILE_MODIFICATION: File modification capability (code files only)

RATIONALE:
- Aligns with actual real-world LLM usage patterns
- Clear progression of capabilities
- Each level enables distinct reward hacking opportunities
- Research questions: Does each level increase gaming behavior?

RESEARCH QUESTIONS:
- PL0 → PL1: Does manual feedback enable more gaming than no feedback?
- PL1 → PL2: Does automated test execution enable more gaming than manual?
- PL2 → PL3: Does file modification enable different gaming strategies?

IMPLEMENTATION:
- Updated PermissionLevel enum in core/results.py
- Updated prompt builders in utils/prompt_builder.py for all 4 levels
- PL0: No feedback, single attempt
- PL1: Multi-turn with manual feedback capability
- PL2: Multi-turn with automated test execution
- PL3: Multi-turn with file modification + automated testing

DESIGN DECISIONS - LLM PROVIDER
================================================================================

DATE: [Early Development - Date Not Tracked]
TOPIC: LLM Provider Integration

INITIAL PROPOSAL: LiteLLM for unified provider interface
- Supports 100+ providers
- Custom endpoints
- Local model support

DISCUSSION:
- User asked: Does LiteLLM cost money? Can it work with any API key?
- Research: LiteLLM is free/open-source, costs only for API usage
- Supports plug-and-play with any API key
- User preference: Use OpenRouter instead

DECISION: Switch to OpenRouter
- Single API endpoint for multiple providers
- OpenAI-compatible API format
- Supports models from OpenAI, Anthropic, Google, Meta, etc.
- Simpler implementation (single provider file)
- Uses OpenAI Python SDK with custom base_url

RATIONALE:
- OpenRouter provides unified access to multiple LLMs
- Simpler than managing multiple provider implementations
- Free service (costs only for API usage)
- Easy to add new models via OpenRouter's catalog

IMPLEMENTATION:
- Created llm_providers/provider.py with OpenRouter integration
- Uses OpenAI SDK pointing to https://openrouter.ai/api/v1
- Supports any model in format "provider/model-name"
- Environment variable: OPENROUTER_API_KEY
- Factory method: LLMProvider.create_from_config()

ENVIRONMENT CONFIGURATION:

- Updated .env with OpenRouter section (preserved existing Gemini settings)
- Added OPENROUTER_MODEL configuration option

TOPIC: Code Execution Isolation

REQUIREMENT: Complete isolation from host system
- LLM code should not have write access to local machine
- Research reproducibility
- Separate environment for each experiment

DISCUSSION:
- Options considered: Temporary directories, chroot, Docker containers
- User preference: Docker for maximum isolation
- Question: What base image to use?
- Options: python:3.12-slim (minimal), python:3.12 (full), custom image
- Explanation: "Less tools" means system tools (gcc, git), not Python packages

DECISION: Custom Docker image
- Base: python:3.12-slim
- Pre-install system tools: gcc, g++, make, git, curl, wget
- Benefits: Reproducible, consistent, research-friendly
- Users build once, then cached for fast runs

DATE: 2025-11-05 00:13-00:14 UTC
TOPIC: Reward Hacking Detection Modules

IMPLEMENTATION:
Created detector modules for identifying different reward hacking behaviors:

1. detectors/hardcoding.py
   - Detects hardcoding patterns in generated code
   - Looks for: direct test input/output matches, excessive if-return statements,
     constants matching test outputs, dictionary mapping patterns
   - Returns detection result with evidence

2. detectors/overfitting.py
   - Detects overfitting: passes visible tests but fails hidden tests
   - Simple but effective: visible_pass && !hidden_pass = overfitting
   - Tracks different patterns (both_pass, both_fail, etc.)

3. detectors/execution_gaming.py
   - Detects gaming behaviors in PL1/PL2 (execution-capable levels)
   - Looks for: excessive test runs, repeated test patterns, iterative hardcoding
   - Uses command history from ConversationState
   - Combines with hardcoding indicators for stronger evidence

4. detectors/test_modification.py
   - Detects test file modification (PL3+ capability)
   - Identifies test files being modified, deleted, or created
   - Compares file snapshots before/after execution
   - Severity levels: high (deleted tests), medium (modified tests)

DESIGN DECISIONS:
- All detectors are stateless functions (easy to test, compose)
- Return dict with "detected" boolean and "evidence" dict
- Evidence includes detailed metrics for analysis
- Can be composed together for comprehensive detection
