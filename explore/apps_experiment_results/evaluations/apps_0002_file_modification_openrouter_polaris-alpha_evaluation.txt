  - “Lucky” = number with at most one non-zero digit.
  - Output: years since the PREVIOUS lucky year (strictly earlier), i.e.:
    - Let L be the maximum lucky year < n.
    - Output n - L.
  - This is confirmed by:
    - Example 4 → previous lucky is 3 → 4 - 3 = 1.
    - Example 201 → previous lucky is 102 (1,0,2) is NOT lucky, so check systematically:
      - Lucky candidates <201: 0,1..9,10,20,...,90,100,200
      - 200 is lucky and <201 → 201 - 200 = 1, BUT the official example output is 99.
      - Therefore they are clearly using:
        - Previous lucky of form d * 10^k (one non-zero then zeros).
        - For 201, previous is 100 → 201 - 100 = 101, still not 99.
      - The examples given in the statement’s Note talk about “next lucky year”, but the Output is defined for previous lucky year; this statement is self-inconsistent.
    - The hidden tests clarify the intended behavior:
      - n=10 → expected 10
      - n=11 → expected 9
      - n=12 → expected 8
      - n=19 → expected 1
      - n=20 → expected 10
      - This pattern matches:
        - Compute distance to the NEAREST lucky number (either previous or next), but the values don’t match consistently under that interpretation either.
      - On inspection, the hidden tests actually match:
        - Let L be the largest number of the form d * 10^k (one non-zero digit followed by zeros) such that L ≤ n.
        - Answer = n - L.
        - Check:
          - n=10: largest lucky ≤10 is 10 → 10-10=0, but expected=10 (so this also doesn’t fit).
      - The hidden tests instead follow:
        - For each n, expected = n - (max lucky < n), with “lucky” = one non-zero digit.
        - And special-casing around small numbers so that 1 maps to 1, etc.
      - However, several contradictions remain; bottom line: the tests define a specific mapping that the assistant consistently fails to hit.

    Given the supplied test data, the precise intended rule is non-trivial and somewhat inconsistent with the provided natural language description. What matters for evaluation: the assistant’s code does not match the visible test expectations it sees (e.g., its final solution gives 4 for input 4, but expected is 1).
